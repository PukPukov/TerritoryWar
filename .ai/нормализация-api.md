# Нормализованный BotAPI

## Решение после исследования
Пользователь уточнил: существующему алгоритму красного достаточно добавить
`api = api.normalized()` в начале move(), включая автоматически преобразуемый
возвращаемый Direction. Никакого api.command(...).

Две стартовые позиции связаны поворотом на 180 градусов. Для синего нормализуем
обе координаты как FIELD_SIZE-1-c, меняем владельцев 1<->2, EMPTY и -1 оставляем.
Соперник представлен в той же системе координат/цветов. TickCount остаётся прежним.
Утилиты next/canMoveTo/towards уже выражены через базовые методы API и переиспользуются
без специальных нормализованных вариантов.

Выделяем маленькое live-view NormalizedBotAPI с парой взаимных enemy-ссылок.
BotState лениво кеширует его только для синего. normalized() красного возвращает
исходный API. Вызов на управляемом API включает нормализованные команды для
текущего move(), в начале каждого move() флаг сбрасывается. Это необходимо:
сам по себе возвращённый enum не несёт системы координат. Повторный normalized()
идемпотентен; формат памяти алгоритма не меняется. Не смешивать raw и normalized
команды в одном move(). Сохранённый view остаётся live, но опт-ин команд требуется
каждый ход — рекомендация ровно пользовательское `api = api.normalized()`.

Единственное преобразование команды в физическое направление выполняется в
общем takeTurn после move и до записи/применения. Direction.opposite() использует
существующий towards(-dx,-dy), включая NONE. Replay хранит только реальные ходы,
поэтому повторная нормализация в playback не нужна; batch/search/live используют
тот же движок. askPoint делегирует в обычный физический UI, возвращённая точка
поворачивается обратно в нормализованный API. UI не меняет цвет и положение поля.

## Перспектива
- Direction — обычный enum без привязки к системе координат. Чтобы пользователь
  мог просто написать api=api.normalized() и вернуть RIGHT, неизбежен контекст
  команды в BotState. Он локален игре/боту/ходу, сбрасывается до каждого move(),
  не является глобальной настройкой. Сохранённый view остаётся live, но для команд
  всё равно надо вызывать normalized() каждый ход. Контракт явно описан в API,
  встроенной справке и здесь, не смешиваем два frame в одном move().
- Конструктор взаимной пары view не проходил initialization checker: исправлено
  ленивой связью уже initialized объекта, а не подавлением проверки.
- Старая cancellation-test fixture имела гонку между победой и управляющей
  отменой: исправлена отдельной политикой gate при одном move; production
  симуляции не менялись. Искусственные задержки/ослабления проверок не добавлены.
- Поворот и смена цветов — адаптация представления, а не второй движок. Новых
  дублирующихся путей движения/записи/поиска не создано. Нормализованная input
  точка возвращается через view, физический UI не копируется и не разворачивается.
