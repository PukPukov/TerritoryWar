## Запуск и сборка

Нужны JDK 25, Maven и установленный родительский `ru.pukpukov:puklapom:1.4.10`
(исходники: `../../lib/puklapom`). Конфигурация JVM для его Checker Framework
включена в `.mvn/`.

```sh
mvn javafx:run
mvn verify -Drelease=false -Dtests.skip=false  # быстрый цикл с тестами
mvn clean package -Dtests.skip=true           # полная компиляция с Checker Framework
java -ea -jar target/territory-war-1.5.jar
```

`clean` при переходе от быстрой сборки к полной нужен, чтобы javac с чекерами
не использовал уже готовые классы Takari. Основной JAR содержит точку входа и зависимости; упаковка целиком наследуется
от puklapom, без локального переопределения поведения shade.
Компиляция алгоритмов — в памяти через [jOOR](https://github.com/jOOQ/jOOR).

## Ручной бот (1.5)

1. Нажмите **Загрузить…** у любого бота, выберите `bots/manual.java` и подтвердите.
   Можно ввести и произвольный путь. Файл примера не изменяется; загруженный текст,
   как обычно, сохраняется в рабочий `bot1.java`/`bot2.java`.
2. Нажмите **Старт**. На запрос точки кликните по основному полю или задайте X/Y
   в попапе. Ручное управление работает для любой стороны, включая двух игроков.
3. Бот идёт ступеньками вдоль прямой: при ΔX:ΔY = 1:3 на один шаг X приходится
   три шага Y. Направления чередуются по исходному сегменту, не буквой «Г».
   Обхода стен нет: достигнув точки или упершись в чужую территорию, бот ждёт
   следующую точку. **Отмена** в попапе оставляет его стоять до сброса игры.

Это обычный код бота, а не отдельный режим движка. Новый API:
- `Direction.NONE` — стоять на месте; `Direction.MOVING` — только четыре направления.
- `api.askPoint()` — блокирующий запрос `BotInput.Point(x, y)`; `null` при отмене.
- `api.towards(start, target)` — следующий осевой шаг по прямому сегменту;
  `api.towards(x, y)` — простой вариант сначала по X, затем по Y. Стены не обходят.

Пока бот спрашивает точку, текущий ход ждёт — второй бот тоже не продвигается,
но окно игры остаётся отзывчивым. **Пауза** останавливает дальнейшие шаги после
завершения текущего хода, **Сброс** закрывает попап и отменяет ожидающий ход.
В пакетах/поиске интерактивного ввода нет: попытка запроса выдаёт явную ошибку.
Завершённые игры через **Старт** сохраняются в списке записей, включая игры с
ручным управлением. Незавершённая игра при **Сбросе** не сохраняется.
Снимки для UI не являются записью и вообще не создаются пакетными симуляциями.

Не пересобирайте JAR, из которого сейчас запущена игра: перезапись архива ломает
отложенную загрузку классов (в том числе шейдеров JavaFX). Закройте игру перед
сборкой или запускайте отдельную копию JAR.

## Симуляции и поиск победы

- **Число игр** задаёт размер пакетной симуляции: по умолчанию 10000, можно ввести
  любое целое число от 1 до 2147483647. **Симулировать** запускает пакет параллельно.
- Выберите **Бот 1** или **Бот 2** и нажмите **Искать победу**. Поиск перебирает игры
  параллельно до первой найденной строгой победы выбранного бота; ничья не подходит. Лимита числа попыток
  нет, кнопка **Отмена** и закрытие окна останавливают поиск между ходами.
  Если бот никогда не побеждает, поиск нужно отменить.
- При поиске сохраняются лучшие завершённые игры по двум оценщикам для выбранного
  бота: **Разница** (его очки минус очки соперника) и **Максимум** (его очки).
  Даже если победы нет, **Отмена** оставляет эти результаты доступными для просмотра.
  При равной оценке сохраняется первая игра; одна игра, лучшая по обоим оценщикам,
  добавляется один раз. Если ни одна игра ещё не завершена, сохранять нечего.
- Выпадающий список **Записи** позволяет выбрать любую сохранённую игру;
  **Смотреть запись** воспроизводит её с начала. Работают
  скорость и пауза; повторное нажатие начинает запись заново. Запись не зависит
  от последующих правок алгоритмов. **Сброс** возвращает обычный режим, но запись
  не стирает. Неудачная/отменённая новая попытка поиска также не стирает её.
- Записи создаются при поиске и в играх через **Старт**. Пакетные симуляции и
  просмотр ничего не записывают. Сохраняются порядок первого хода, итоговые очки и реальные
  направления/пропуски ходов; воспроизведение использует тот же движок и правила,
  а не повторно запускает случайный алгоритм. Поиск не накапливает все попытки:
  остаются только лучшие игры по оценщикам.
- Библиотека хранится **в памяти до закрытия приложения**, экспорта на диск пока нет.
  Хранилище выделено в интерфейс `GameLibrary` с реализацией `InMemoryGameLibrary`;
  файловую реализацию можно добавить без изменения логики поиска.
  Код ботов выполняется без песочницы: зависший внутри `move()` алгоритм нельзя
  принудительно безопасно прервать, отмена проверяется между вызовами.

Пакет и поиск используют один многопоточный цикл: число рабочих задач определяется
числом доступных CPU (минимум две), для маленького пакета — не больше числа игр.
Победа останавливает остальные попытки между ходами; сохраняются лучшие записи
по оценщикам, в том числе найденная победа по **Разнице**. Учитываются только завершённые и принятые до остановки игры, не начатые
попытки. При поиске одновременно в памяти находятся записи активных игр; в пакете
записи полностью отключены. Ошибка и отмена также останавливают всех workers.

Правила сохранены: замкнутые области заполняются один раз **в конце** игры.
Исключение выполнения бота означает пропуск хода с сообщением в логе; ошибки
инвариантов и VM не маскируются под пропуски. Ошибка создания бота прерывает
симуляцию и показывается, а не исчезает из итоговой статистики.

## Проверки

Тесты фиксируют поведение исходного движка, порядок ходов, точность каждого тика
записи, отсутствие записи в пакетах, число игр, отмену с сохранением лучших игр,
независимость оценщиков, библиотеку и диагностику компилятора.
Для интеграционного теста JavaFX нужен графический сеанс:

```sh
mvn test -Drelease=false -Dtests.skip=false -Dui.test=true
```

UI проверяется дочерним процессом во временной папке: пользовательские `bot1.java`
и `bot2.java` не изменяются.

Синхронизация кода с диском сохраняет локальную версию в соседний
`*.conflict-*.java` и уведомляет при обнаружении одновременных правок; затем
загружается версия с диска. Сохранение атомарное: если файловая система не
поддерживает `ATOMIC_MOVE`, показывается ошибка вместо тихого неатомарного обхода.

Проверка основного JAR после сборки:

```sh
mvn test -Drelease=false -Dtests.skip=false -Dtest=JarPackagingTest -Dpackaged.jar=target/territory-war-1.5.jar
```
