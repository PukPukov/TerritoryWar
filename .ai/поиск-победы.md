# Рефакторинг Territory War и поиск победы — 21.10.2026

## Решение
Приоритет — сократить логику, затем добавить поиск и настройку количества игр.
Прочитаны инструкции GANCAP для исполнителя и пример DirectoryCompacter.
Граф Territory War проверен на актуальность и покрытие всех используемых исходников.

Обнаружено: состояние и операции двух ботов продублированы; направления вычисляются
в API, движке и flood fill отдельно; очередь flood fill дополнительно копируется
в region-массивы; UI занимается компиляцией и многопоточностью, глотает ошибки
конструкторов ботов; на каждую симуляцию ставится событие в FX-очередь.
BotCompiler вручную пишет временный исходник и неверно вычисляет путь очистки
(старый пакет com.territorywar). CodeSyncManager при ошибке чтения способен затереть
пользовательский файл дефолтным кодом, содержит sleep вместо объяснённого протокола.

План: единый GameEngine для живой игры, симуляций и просмотра. Массив состояний
ботов, одна реализация направления, одна очередь flood fill. Записывать только
поиск: начальный порядок + фактически возвращённые ходы (включая пропуски).
Воспроизведение подаёт записанные ходы обычному движку, не перезапускает алгоритмы.
Симуляции и создание ботов — небольшой отдельный класс; JavaFX Task управляет
фоном/прогрессом/отменой. Количество задаётся для пакетных симуляций (10000 по
умолчанию), поиск выбранного победителя неограничен до победы или отмены.
Запись последней найденной победы хранится в памяти до закрытия приложения.
Сборка наследует puklapom 1.4.10, без повторения его конфигурации.

## Промежуточная проверка
Baseline снят до изменений для 3 сценариев и обоих начальных порядков:
число тиков, все позиции/очки на каждом тике, весь итоговый grid (CRC32).
13 исходных новых тестов прошли. Полная clean-сборка запустила Checker и прошла.
Найден нюанс puklapom: без packaging=${jarLifecycleType} быстрый профиль отключает
javac, но не включает Takari lifecycle; исправлено. После смены lifecycle нужна
реальная перекомпиляция (clean), иначе сообщение «успех» не проверяет исходники.
Shade подключён как отдельный artifact, чтобы инкрементальная сборка не шейдила
повторно уже fat JAR. Добавлен UI-тест в изолированном дочернем cwd.

Независимое ревью подтвердило гонку ошибок parallel stream и конфликт debounce
с внешним редактированием. Исправлено: общая причина ошибки сохраняется в
AtomicReference; при конфликте обе версии сохраняются (локальная — в соседний
`.conflict-*.java` с уведомлением), а watcher и save используют одну проверку.
Тест конфликтов вызывается также до watcher, через close/flush, чтобы покрывать
именно исходную гонку. ATOMIC_MOVE без поддержки FS выдаёт явную ошибку, не тихий
неатомарный fallback. Это сознательное ограничение, не замаскированный сбой.

Визуальный QA на 800×500 выявил регрессию: сетка, нарисованная поверх территорий,
при cellSize=1 закрывает их цвет. Вернул исходный порядок слоёв (сетка под цветными
клетками) и добавил в UI-тест проверку наличия цвета территории в snapshot.

Пользователь параллельно перевёл BotState на Lombok @Getter и добавил
lombok.config с fluent=true; правки сохранены, поле ticks стало tickCount.
Промежуточные компиляции попали на незавершённое редактирование; итоговую
проверку запускаю с хешами исходников до и после, без отката пользовательского кода.
Резервная копия промежуточного пользовательского GameEngine сохранена отдельно.
Исчезнувший во время работы пользовательский output.txt не восстанавливал:
ни исполнитель, ни QA его не удаляли, это стороннее изменение workspace.


## Итог
Рефакторинг выполнен без отдельного игрового алгоритма для записи. Состояние
ботов и их ходы обрабатываются одинаково; направления определены один раз в enum,
API и движок используют их. Финальная заливка использует одну BFS-очередь вместо
четырёх массивов и не выделяет рабочую память на весь срок обычной игры.
Ручной временный compiler/classloader заменён jOOR, конфигурация сборки — puklapom.
Инфраструктура фона и прогресса — стандартный JavaFX Task, без собственного executor.

Поиск принимает выбранного победителя, игнорирует ничьи и останавливается только
при победе/отмене. Пишет два байта на тик и исходный порядок; сохраняет только
найденную игру. Просмотр, обычная игра и пакет не выделяют буфер записи. Просмотр
не запускает оригинальные алгоритмы и не зависит от их текущего текста/случайности.
Размер пакета настраивается в UI, значение по умолчанию 10000.

Пользовательские @Builder/fluent API интегрированы во все вызовы, включая replay
и тесты. Пользовательские staged/unstaged изменения не откатывались.

Проверено на финальных исходниках с совпавшими хешами до/после сборок:
- `mvn verify -Drelease=false -Dtests.skip=false -Dui.test=true -fae` — 18/18.
- `mvn package -Dtests.skip=true -fae` с принудительной актуализацией timestamp
  production-исходников — реальный javac+Checker, BUILD SUCCESS.
- Сравнение исходного движка по baseline, покадровый replay, конечная заливка,
  случайные и пропущенные ходы, обе стороны поиска, отмена в середине игры,
  ошибки конструкторов в параллельном пакете, компиляция текущих ботов.
- UI-проход в изолированной папке: 7 игр, поиск/повтор записи при изменённом
  исходнике, отмена, ввод неверного количества, внешний reload и конфликт правок.
- Snapshot 800×500 проверен визуально и тестом цвета территории.
- Исполняемый shaded JAR отдельно проверен: компиляция алгоритма в памяти,

- Независимый сборочный/архитектурный review выполнен, найденные реальные дефекты
  гонки ошибок и конфликта синхронизации исправлены и покрыты регрессиями.

## Перспектива
Общие игровые пути не продублированы. Различаются только управляющие циклы:
конечный параллельный пакет и последовательный неограниченный поиск вызывают один
`play`/`logicTick`; playback подставляет поток направлений в тот же движок.
Поиск последовательный, поэтому держит запись лишь текущей попытки, не нескольких
параллельных игр. Новых альтернативных правил движения/подсчёта/заливки нет.

Сохранены явные ограничения: запись — только в памяти до закрытия; пользовательский
Java не изолирован, зависание внутри move нельзя безопасно принудительно прервать;
компиляция по кнопке остаётся синхронной на FX-потоке. На FS без ATOMIC_MOVE
сохранение выдаёт явную ошибку. Детектируемые конфликты сохраняют обе версии;
остаётся узкое TOCTOU-окно между чтением внешнего файла и atomic rename, поскольку
сторонние редакторы не участвуют в общей транзакции/блокировке. Полноценный
многопользовательский файловый протокол ради двух локальных файлов не добавлялся.

Граф имеет известные parse gaps на import module java.base и не видит Lombok-
генерацию полностью; структурные выводы проверены исходниками и реальной компиляцией.
В контейнере UI/JAR проверены через JDK из JAVA_HOME (Graal25). Системный JBR при
отдельном CLI smoke не нашёл libgthread-2.0; это зависимость JavaFX GTK окружения,
не обходилась изменениями игрового кода.

## Исправление упаковки основного JAR — 21.10.2026
Причина `no main manifest attribute`: локальное `shadedArtifactAttached=true`
переопределяло штатную упаковку puklapom и оставляло основной artifact тонким JAR.
Это моя регрессия: исходная команда java -jar должна была сохраниться.
Решение: удалить только переопределение, использовать Main-Class/зависимости,
уже настроенные родительским POM, без дублирования манифеста или новых плагинов.
Старое решение с отдельным -shaded.jar отменено. Версия пользователя 1.4 сохранена.
Резервные копии pom/README и обоих JAR: /tmp/territory-war-packaging-backup/.
Постоянный JarPackagingTest проверяет именно основной JAR после package:
Main-Class, Launcher и классы JavaFX/jOOR. До фикса он воспроизводит исходный сбой.

Проверка исправления упаковки: быстрая verify с UI — 18 успешных тестов
(условный packaging-тест отдельно пропущен до package); штатный release package
успешен; JarPackagingTest после package — 1/1. Основной territory-war-1.4.jar
теперь содержит Main-Class Launcher и runtime-зависимости. Прямой запуск
`java -jar` проверен в изолированном cwd: процесс работал до остановки тестовым
4-секундным timeout, ошибок манифеста/классов/инициализации JavaFX не было.
Локальная конфигурация манифеста/шейдинга не добавлялась — работает puklapom.
