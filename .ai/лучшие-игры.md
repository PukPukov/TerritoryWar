# Лучшие результаты поиска и runtime библиотека игр

## Решение после исследования
Нужны два независимых оценщика: разница очков выбранного бота с соперником и
максимум его очков. После отмены возвращаем статистику и лучший завершённый
матч для каждого оценщика; одна игра, лучшая по обоим, хранится один раз.
Идея «в памяти» не означает хранения в UI: GameLibrary — маленький интерфейс
add/entries, InMemoryGameLibrary — список. Выпадающий список только отображает
library, в будущем интерфейс можно реализовать файловым хранилищем.

GameReplay дополняется итоговыми очками (это метаданные записи, не второй снимок).
Simulations.Result содержит map оценщик->запись и cancelled. В общем worker-loop
держим до двух лучших завершённых GameEngine, не копируя буфер на каждое улучшение;
после join создаём уникальные записи. Отмена — штатный Result, ошибки — исключения.
В UI отмена теперь устанавливает stop flag, а не Task.cancel: JavaFX отменённый
Task отбрасывает возвращённое значение. Кнопка/закрытие ждут остановки workers,
потом общий success-путь показывает статистику и добавляет результаты в library.

Все завершённые игры через Start записываются и добавляются в library, playback
не записывается повторно, batch остаётся без записи. Это явное новое пожелание
пользователя, заменяющее ранний запрет записи обычной игры. Незавершённые игры при
Reset не сохраняем: движок/replay сейчас оперируют завершёнными матчами.
Пользовательские боты не читаем и не тестируем.

## Отчёт
Реализованы оба оценщика и независимое от JavaFX хранилище с интерфейсом
`GameLibrary` (add/entries) и реализацией `InMemoryGameLibrary`. Никаких SQL,
сервисов и дополнительных фреймворков. Записи имеют название и финальные очки,
выбираются через dropdown. Для дискового backend достаточно реализовать контракт
хранилища и добавить сериализацию GameReplay; дисковый формат сейчас не навязываем.

Общий параллельный цикл batch/search сохранён. Сравнение кандидатов выполняется
только в поиске, под существующим lock статистики; до завершения workers держатся
сами лучшие GameEngine, записи копируются один раз после join. Отмена сохраняет
частичный результат вместо исключения, остальные ошибки по-прежнему видимы.
В UI отмена и штатное завершение используют один success-путь. Все завершённые
игры Start используют тот же движок и общий addRecording с результатами поиска.

Пользователь подтвердил завершение параллельных правок перед финальной сборкой.

## Перспектива
- Незавершённый Start при Reset не сохраняется: текущая запись означает полный
  матч. Для сохранения незавершённых партий нужен явный контракт окончания replay,
  а не подмена результата частичного поля итогом полной игры.
- Библиотека живёт до закрытия приложения и растёт с числом сохранённых игр.
  Ограничение объёма, удаление и сериализация не добавлялись без запроса.
- Лучшие результаты — среди матчей, принятых до остановки, а не среди ещё
  выполнявшихся попыток. Победа и отмена штатно останавливают соседние workers.
- Исторический Task.cancel терял возвращаемый Result; исправлен контракт отмены
  сквозным флагом и единым success-путём. Отдельный цикл для поиска не создан.
- UI имеет разные источники запуска (live/playback и batch/search), но правила,
  исполнение ходов и воспроизведение используют один GameEngine; архивирование
  проходит через один метод. Новых дублирующих путей правил не добавлено.
