# Параллельный поиск победы

## Исследование и план
Сейчас batch использует parallel IntStream, поиск — do/while на одном потоке.
Оба выполняют общий play, но управляющие циклы разошлись. Пользователь попросил
не добавлять второй многопоточный путь, а сделать практически один алгоритм.

Решение: один ограниченный набор worker-loop через parallel IntStream для обоих
режимов. Общая выдача игр, один newGame/logicTick, общий stop-предикат между ходами,
общая фиксация завершённых результатов и прогресса. У batch есть счётчик оставшихся
игр, у поиска атомарно опубликованная запись победителя. Ведём только один найденный
replay; незавершённые попытки не считаем. Worker-ы штатно выходят при победе/отмене/
ошибке, parallel terminal operation дожидается всех. Ошибка сохраняет cause и тип,
не заменяется искусственным CancellationException соседнего worker-а.
Поиск ограничен числом CPU (минимум 2 workers), не unbounded parallel stream.
Запись у batch выключена, у каждой поисковой попытки включена. Копируется/сохраняется
только одна выигравшая запись, остальных snapshots/UI нет.

Тестировать только ядро: fake Bot fixtures для гонки winner/остановки, ни чтения,
ни запуска пользовательских bots/*.java. Проверки до и после изменений обязательны.

## Ревью
Независимый read-only проход подтвердил общий worker-loop и корректность границ
stats/replay/progress под одним lock, сохранение исходных ошибок и join перед
возвратом. Отрицательный remaining после исчерпания пакета — ограниченный sentinel
(не более числа worker-ов), не приводит к лишним играм; отдельный CAS-алгоритм
ради косметического запрета отрицательного значения не добавлялся.

Обнаружил и сообщил повторную ошибку процесса сборки: verify тоже включает package
и попал на уже запущенный пользовательский JAR. Дальнейшая сборка была остановлена;
после явного сообщения пользователя «выключил» добавлена проверка /proc на запуск
именно territory-war-1.5.jar перед финальной упаковкой. Не убивал процессы/не скрывал
эту проблему. В будущем тесты при открытой игре запускать через test, не verify.


## Итог
В Simulations.run теперь один parallel worker-loop, без отдельных алгоритмов для
пакета и поиска. Код run стал короче (по сравнению с исходным staged состоянием
минус 3 строки), дополнительных executor-ов/классов/очередей нет. Число worker-ов
CPU-bounded (минимум2, не больше count в конечном пакете). stop общий; batch без
записи, поиск с записью текущих попыток. Под lock фиксируется только первая
принятая победа, остальные попытки выходят между ходами. Выход `run` происходит
после завершения всех worker-loop, статистика/прогресс после выхода не меняются.

Проверено на конечном коде:
- реальный многопоточный запуск поиска для обеих сторон, конкурентная отмена,
  join после победы/отмены, сохранение и воспроизведение только принятой победы;
- конечный пакет ровно N игр, последовательный монотонный progress callback;
- сохранение исходной причины параллельных ошибок и для batch, и для поиска;
- `mvn package -Dtests.skip=true -fae` — 15 production-файлов реально

## Перспектива
Отдельных путей логики batch/search больше нет. Различаются только условия выдачи
следующей игры и предикат принятия победы; запуск/ходы/прогресс/остановка общие.
Побеждающая запись недетерминирована по порядковому номеру попытки: это первая
принятая завершившаяся победа. Память выше однопоточного поиска: одновременно
хранятся буферы активных поисковых игр (ограничено числом worker-ов), а не только
один. На однопроцессорном окружении две задачи добавляют переключения контекста,
но обеспечивают многопоточную семантику. Зависший внутри пользовательского move
Java-код всё ещё нельзя безопасно прервать: остановка между вызовами, без unsafe
thread stop. Рабочие задачи используют штатный common ForkJoinPool, поэтому
явные JVM-ограничения его parallelism влияют на реально доступные потоки.
