# 1.5 — ручной бот через обычный API

## План после исследования
Нового режима движка нет. Пример тела Bot.move живёт в отслеживаемом bots/manual.java.
Direction.NONE=(0,0), towards вычисляет простое направление (сначала X, потом Y).
BotAPI.askPoint блокирует ход, UI предлагает клик по полю или координаты в попапе.
Никакого обхода стен: при достижении/упоре бот спрашивает следующую точку.
При отмене ввода пример дальше возвращает NONE. Пока открыт запрос, ход ждёт:
остальные боты тоже не ходят, счётчик idle не тикает.

Обнаружено: live logicTick сейчас идёт на FX-потоке, блокирующий бот заморозит UI.
Переносим live тики в JavaFX Task (один batch одновременно); UI работает только с
снимком поля, а не читает изменяемый движок worker-потока. Пакеты/поиск остаются без
снимков и без записи вне поиска. У интерактивного API явная недоступность в headless
симуляциях, не маскируем её как ошибочный пропуск хода. Reset/закрытие отменяют Task
и попап; Pause не прерывает середину хода, только останавливает следующие шаги.
Встроенный sample можно загрузить из файла в любой редактор, текущий пользовательский
алгоритм не перезаписывается автоматически. Нужна кнопка загрузки бота из файла.

## Найденные и решённые вопросы
- Пользователь попросил пропорциональную диагональ: добавлен перегруженный
  BotAPI.towards(start,target) с midpoint-распределением осевых шагов; отношение
  считается относительно исходного сегмента, не меняющегося остатка расстояния.
- Проверки пользовательских ботов прекращены по просьбе пользователя. Ранее manual
  уже проверялся, но новые алгоритмы не проверяются; тесты оставлены на ядро/API.
  UI использует фиксированный драйвер API во временной папке, не bots/manual.java.
- Нативный GTK FileChooser реально падал у пользователя из-за отсутствующих
  GSettings schemas. Вместо установки зависимостей/перехвата fatal использованы
  стандартные JavaFX Dialog+editable ComboBox: примеры bots и произвольный путь.
- Пользователь подтвердил CNFE shader при пересборке запущенного JAR. Класс/ресурс
  присутствуют в jar; воспроизведение на копии: открыть fat jar classloader-ом,
  перезаписать thin jar -> CNFE FillRoundRect_Color_Loader (причина EOF).
  Не добавляем software rendering workaround. Проверка упаковки грузит все
  shader loader классы, включая FillRoundRect_Color_Loader.
- Независимое ревью: ошибка popup-моста могла превратиться в пропуск хода:
  введён BotInput.Failure с cause, takeTurn не проглатывает ошибки ввода.
  Пауза после завершения больше не заменяет победителя; на worker состояние не
  читается с FX пока step активен. Пауза действует только на границе текущего хода.

## Перспектива
Нет отдельной реализации движения или режима для человека: обычный Bot.move
получает обычный BotAPI, выбирает цели и возвращает Direction. NONE идёт через
тот же takeTurn; flood fill использует тот же список MOVING без лишнего zero-соседа.
Новая инфраструктура состоит из capability BotInput (без JavaFX в API), PointInput
для FX↔worker ожидания и BoardState для безопасной публикации видимого состояния.
Снимки — текущий кадр, не запись; у batch/поиска ни снимков, ни popup нет.

Компромиссы: блокирующий запрос останавливает всю последовательность ходов, не
только человека (согласовано пользователем); Pause не прерывает середину move.
Отмена popup в примере означает стоять до сброса, а штатный idle-лимит игры затем
может завершить матч. Очереди будущих точек нет: следующий запрос после достижения
или упора. Шаги на пути не обходят чужую территорию и не ищут альтернативный маршрут.
Снимок копирует grid только в live-показе; фоновые тики добавляют одну Task/virtual
thread на batch, а не на каждый ход. Пользовательский Java вне песочницы всё ещё
может игнорировать interruption или сам затереть память; принудительного unsafe stop
не добавлял. JavaFX предупреждения native access/unnamed module остаются предупреждениями,
не скрывались флагами/перехватом исключений в production.
